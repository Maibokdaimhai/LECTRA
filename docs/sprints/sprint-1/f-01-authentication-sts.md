## 1. Execution model, fixtures and result records

IDs use `TEST-F01-Uxx` for unit, `Ixx` for API/real-PostgreSQL integration, `Exx` for selected browser/E2E, `Mxx` for justified manual/process checks and `Hxx` for actual domain integration handed to dependent work. AC references use the full `AC-F01-xx` IDs defined in the contract; abbreviated numeric ranges below refer to that prefix. Every expanded parameter row is an individual assertion/scenario in the actual implementation, even when grouped under one stable design ID.

Proposed locations after setup: API unit `apps/api/src/auth/**/*.test.ts`, real DB/API `apps/api/tests/auth.integration.test.ts`, browser `tests/e2e/auth.spec.ts`. These are plans, not files asserted to exist. #15 defines actual scripts/runner/config and records reproducible commands. Do not copy a command into evidence before it exists and runs. Use Vitest for units, Supertest for HTTP integration, real PostgreSQL for store/User/schema and Playwright against the actual app/API for browser cases.

| Fixture / control | Contract for future execution |
| --- | --- |
| Users O-A/O-B and R-A/R-B | Separate UUIDs; OWNER/RESPONDENT roles; `.test` synthetic emails; display names; unique salted Argon2id hashes. Keep plaintext synthetic password variables only in explicit local/test setup, not logs/evidence. |
| Session jars A/B | Independent cookie jars and guest bootstrap tokens, then real login where required. Save an old signed cookie only in test memory for replay/fixation assertions; redact it from snapshots/reporters. |
| Database | Disposable allowlisted PostgreSQL test database with reviewed User/auth_session migrations. Assert DB name/URL safety before reset; no dev/deployed DB credentials or destructive reset there. Run suite-isolated data or serialize destructive session tests. |
| Time | Inject server clock/limiter clock through test composition, never via a public header/query parameter. Use real DB session rows and explicitly controlled expiry values; do not wait eight hours or 15 minutes. Browser and store expiry behavior must still be checked, not only a mocked helper. |
| Failures / barriers | Inject failing store/DB operation at test composition boundaries; retain real DB assertions for before/after state. Use barriers to overlap read/logout rather than race-prone sleeps. Fault injection is not a replacement for normal real persistence tests. |
| Data snapshots | Capture row counts/identities and safe state before/after rejection. Assert no new authenticated row and no unauthorized mutation; a guest CSRF row is not itself an authenticated login. |
| Public deployment profile | Local TLS/proxy test fixture or equivalent verified cookie/transport harness with exact trusted path; cloud resources are not assumed. Label response-header-only cookie inspection separately from actual browser Secure-cookie behavior. |

For each actual result retain: stable test and AC IDs, source/test file and case name, command, date, runtime/OS/lockfile/schema, tested SHA, expected/observed result, counts and output reference. Report failed/skipped cases and unresolved dependencies. No screenshot alone proves server revocation or DB persistence. Do not upload cookies, raw session JSON, hashes, tokens or credentials as evidence.
