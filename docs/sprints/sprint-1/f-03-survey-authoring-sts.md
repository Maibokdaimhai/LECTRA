# F-03 — Software Test Specification

Version 0.1 · 2026-11-07 · Issue #12 · **Every case: Planned / Not run.**

## 1. Scope and execution boundary

This is the preimplementation test design for the [F-03 engineering contract](f-03-survey-authoring.md), especially §§2–9. It specifies 40 stable cases linked to 26 AC; it contains no application test code, executed results, passing assertions or review approval. U = unit; I = API with real PostgreSQL; E = selected UI/E2E; M = supplementary/process; H = cross-feature handoff. Subscenarios within a case must be independently asserted/parameterized when implemented; 40 planned specification cases are not a prediction of runner assertion/test counts.

The contract's §9 table is the forward AC→test index. The linked-AC column below is the reverse index; `AC-F03-xx` always refers to that table, and all case IDs begin `TEST-F03-`. No AC is satisfied merely by writing a case. F-04 answer validation and F-05 calculations are not reimplemented in F-03 unit tests; H02/H03 require the real accepted adjacent feature implementations before they can be recorded as executed integration evidence.

## 2. Fixtures, harness and result recording

Use synthetic Owner A and Owner B with distinct Sections of the same Course; each owns at least two Lectures. Respondents R1/R2 belong to A's Section, R3 only to B's, R4 initially outside A's. Include an owned empty Lecture and Draft/Published/Closed surveys on different Lectures (one Survey per Lecture). Include both empty/incomplete Draft and complete 1-RATING/10-question definitions, optional TEXT and explicit scale meaning such as slow→fast. Publication fixtures must include frozen Eligibility; current Membership alone is not enough. F-04-populated fixtures with Participation/ResponseBundle/Answers are required where preservation is asserted. #16 owns migrations/seeds; isolated test setup may insert invalid role Membership to prove publication rejects it, but no production admin API is added.

Use accepted Vitest/Supertest/Playwright tooling after #15/#16 exist. Integration uses real migrated PostgreSQL, real HTTP middleware and F-01 sessions/CSRF (unless a unit case explicitly isolates pure logic); never substitute SQLite/in-memory repositories for transaction/access evidence. Independent connections and explicit barriers prove both race orders; record affected row counts and complete before/after snapshots. Do not infer serialization from Promise scheduling, sleeps, mocked locks or only response codes. Test setup resets isolated data, not another developer's database.

All negative mutation checks assert no persisted changes to Survey/Question/Eligibility and any seeded response rows. Auth/ownership tests use otherwise valid payloads and valid CSRF where needed so they reach the intended boundary. On errors inspect response headers/body and captured safe logs. Fault injection is a test-only seam or controlled DB failure, never an application endpoint; distinguish known rollback from lost commit acknowledgment. E2E uses real APIs/database and isolated sessions; no mocked success response can prove persistence.

When implemented, record actual test file/name, command, environment/DB version, immutable tested SHA, expected/observed outcome, pass/fail/skip counts, safe artifacts and review references. Document failed and skipped cases honestly. A documentation check is not application execution. Current result for **every row below is Planned / Not run**.

## 8. Meaningful TDD candidates and completion gate

Choose a small, genuine sequence during implementation, preserving actual failing and passing output against the actual versions. Do not create retrospective RED records or count import/syntax failure as intended-behavior RED. Suitable candidates:

| Rule | Planned candidate cases | Intended RED assertion before behavior exists | Intended GREEN evidence |
| --- | --- | --- | --- |
| Stable whole-definition revision/order | U05, I05, I09 | Retained question ID/order or stale-write rejection fails an intended assertion | Correct DB rows/revision and no lost update under real concurrency |
| Unique Lecture Survey | I03 | Competing creation fails exact one-Survey/409 assertion | Real PostgreSQL unique constraint and safe mapping produce expected outcome |
| Publish freeze | I12,I13,I15,I16 | Partial snapshot or wrong race/eligibility boundary violates assertion | Atomic state/snapshot and both controlled race orders proven |
| Close serialization and rollback | I19,I20; later H02 | Close-first protocol admits response or failure leaves partial rows | Real locked transactions reject/preserve correctly; later real F-04 integration independently recorded |

Candidate selection is a plan, not an obligation to invent one RED/GREEN artifact for every parameter. Important rules still require the full relevant planned coverage, even if a different genuine TDD slice is selected. A unit GREEN does not replace real DB/handoff results.

Before implementation: review both documents and resolve contract §11, including accepted PR #29/#11 versions, #16 migration/lock/reorder/snapshot design, #13 close/submit protocol and #14 frozen scale/privacy. Before feature acceptance: implement mapped cases, record actual outcomes and failures/skips, complete substantive teammate review and reproducible setup, and retain actual versions/history. Before release: #22/#23 integrated verification, #25 accepted main release and #26 actual evidence/PDF gates remain separate. No gate is marked complete by this STS.
